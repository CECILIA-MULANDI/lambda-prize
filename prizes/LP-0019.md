# LP-0019: BTC–LEZ Adaptor Signature Swap: Feasibility Study [DRAFT]

**`Status: Draft - pending LEZ timelock feature and LEZ compute unit metering`**
**`Logos Circle: N/A`**

## Overview

This prize targets a focused feasibility study and prototype demonstrating that **adaptor signatures** can serve as the cryptographic foundation for a trustless Bitcoin–LEZ atomic swap. Unlike Hash Time-Locked Contract (HTLC) approaches, adaptor signatures enable swap transactions that are indistinguishable from ordinary payments on both chains — a meaningful privacy property that HTLCs cannot provide.

The prize has three interlocking objectives:

1. **Prototype** a minimal LEZ Risc0 program that verifies an adaptor signature relationship or extracts an adaptor secret from a completed signature, and demonstrate end-to-end swaps in **both directions** (BTC→LEZ and LEZ→BTC) on testnets.
2. **Benchmark** the cost of the required elliptic curve operations (ECDSA / Schnorr on secp256k1) inside the Risc0 zkVM, and document the compute unit (CU) budget consumed per swap operation.
3. **Analyse** the on-chain privacy achievable when both the Bitcoin and LEZ legs use adaptor signatures and private state, comparing it to HTLC-based and public-state alternatives.

This prize produces artefacts that directly inform and de-risk [LP-0006 (Atomic Swap with LEZ)](LP-0006.md), specifically its Bitcoin leg, and answers open questions about cryptographic feasibility before that larger prize is fully opened.

> **Note:** This prize is currently in **Draft** status because the following dependencies are not yet available:
> - **LEZ timelock**: LEZ does not yet support on-chain timelocks, which are required for the refund path of the swap protocol.
> - **LEZ compute unit metering**: LEZ does not yet expose a stable per-transaction compute unit budget, which is required for the Performance criteria (CU cost per escrow operation).
>
> The prize will open once both are available.

## Motivation

[LP-0006](LP-0006.md) specifies a production-grade atomic swap across Bitcoin, Monero, and Ethereum. Before that work begins in earnest, two open questions about the Bitcoin leg need concrete answers backed by working code:

- **Performance**: secp256k1 elliptic curve operations are expensive inside a general-purpose zkVM. How many Risc0 cycles does it take to verify a Schnorr adaptor signature, extract a secret, or perform a scalar multiplication? Are these counts within the practical compute budget for a LEZ transaction?
- **Privacy**: LEZ has shielded balances and private state as first-class primitives. What combination of Bitcoin-side adaptor signatures and LEZ-side private state delivers the strongest privacy guarantee — and what metadata still leaks?

HTLCs impose three well-known privacy costs: they use non-standard scripts (identifiable on-chain), the hash preimage links the two legs of the swap, and the script is revealed when spent. Adaptor signatures solve all three on the Bitcoin side — the spending transaction is a plain Taproot key-path spend with no visible script, no preimage, and no cryptographic link to the other leg. Whether the LEZ side can match this with private state is an open question this prize is designed to answer.

A competitive prize is the right mechanism because the optimal approach to verifying secp256k1 operations inside Risc0 — pure-Rust crates, guest-side optimizations, alternative scalar representations — is a design question with non-obvious performance trade-offs.

## Success Criteria

### Functionality

- [ ] A LEZ Risc0 guest program is implemented that accepts an adaptor secret *t*, verifies *T = t·G* against a committed adaptor point, and releases or refunds an escrowed amount of the native LEZ token.
- [ ] The program correctly verifies a BIP-340 Schnorr adaptor signature: given a pre-adaptor signature, the adaptor point *T*, and the completed on-chain signature, the guest verifies that *t* was the adaptor secret and the signature is valid.
- [ ] Complete end-to-end swaps in **both directions** (BTC→LEZ and LEZ→BTC) are demonstrated on Bitcoin testnet and LEZ devnet/testnet using adaptor signatures (not HTLCs) on the Bitcoin side.
- [ ] The Bitcoin transaction is a valid Taproot key-path spend — no custom script appears on-chain; the adaptor mechanism is entirely off-chain.
- [ ] Both the happy-path (swap completes) and the refund-path (timelock expires, funds recovered) flows are demonstrated.

### Performance

- [ ] **ECDSA on secp256k1 inside Risc0**: Measure and document the Risc0 cycle count for ECDSA signature verification inside a guest program. Report the median cycle count over at least 20 runs per crate.
- [ ] **Schnorr on secp256k1 inside Risc0**: Measure and document the cycle count for BIP-340 Schnorr signature verification (adaptor and non-adaptor forms) inside a guest program. Report the median over at least 20 runs per crate.
- [ ] **Adaptor secret extraction**: Measure the cycle count for extracting *t* from a completed Schnorr signature and a pre-adaptor signature inside the guest. Report the median over at least 20 runs.
- [ ] **Comparison table**: Provide a table comparing cycle counts for each operation across at least two Rust crate implementations (e.g., `k256`, `secp256kfun`).
- [ ] **CU cost per swap operation**: Document the compute unit (CU) cost of each LEZ escrow operation (lock, release with adaptor secret, refund) on LEZ devnet/testnet. Note: LEZ's per-transaction compute budget system must be available and stable for this criterion to be evaluated.
- [ ] **Feasibility verdict**: State explicitly whether the measured cycle counts are within the practical per-transaction compute budget for LEZ testnet 0.2. If not, document what would be required (e.g., a secp256k1 precompile for Risc0) to make them feasible, and provide a rough estimate of the cycle savings expected.

### Privacy

- [ ] **Privacy model documentation**: Provide a written analysis comparing the on-chain privacy of the following four combinations (two Bitcoin mechanisms × two LEZ state models), documenting what is visible on each chain and what cross-chain correlations remain:

  | # | Bitcoin side                   | LEZ side                |
  |---|--------------------------------|-------------------------|
  | 1 | HTLC (P2WSH)                   | Public escrow account   |
  | 2 | HTLC (P2WSH)                   | Private/shielded escrow |
  | 3 | Adaptor sig (Taproot key-path) | Public escrow account   |
  | 4 | Adaptor sig (Taproot key-path) | Private/shielded escrow |

- [ ] **LEZ information leakage**: For each step of the swap protocol on LEZ, document what information is visible on-chain and which account type (public or private/shielded) must be used — e.g. which steps require a public escrow account, which can use a shielded account, and what an observer can infer from each transition.
- [ ] **LEZ private state feasibility**: Assess whether the LEZ private state model allows the Risc0 guest to both verify the adaptor signature relationship and update shielded state in a single transaction, or whether a two-step commit-reveal is needed. State clearly what was tried and what was found.
- [ ] **Path to LP-0006**: State explicitly what additional work is needed to extend this prototype to the full BTC leg of LP-0006 (maker/taker model, concurrent swaps, Logos Delivery/Chat integration).

### Usability

- [ ] A module/SDK exposing the LEZ adaptor signature escrow operations is provided for use in Logos modules.
- [ ] An IDL for the LEZ escrow program is provided using the [SPEL framework](https://github.com/logos-co/spel).

### Supportability

- [ ] The LEZ program is deployed and tested on LEZ devnet or testnet 0.2.
- [ ] End-to-end integration tests run against a LEZ sequencer (standalone mode) and are included in CI.
- [ ] CI must be green on the default branch.
- [ ] A README includes: deployment steps, program address, step-by-step instructions for running both demo flows, and benchmark reproduction instructions.

- [ ] A written technical report in the repository covers: adaptor signature protocol design, LEZ escrow design, performance benchmarks, privacy analysis, open problems, and recommended integration path to LP-0006.

## Scope

### In Scope

- A minimal LEZ Risc0 guest program (Rust) that verifies a BIP-340 Schnorr adaptor signature relationship and releases or refunds an escrowed native LEZ token amount.
- Benchmarking of secp256k1 ECDSA and Schnorr operations inside the Risc0 zkVM, comparing at least two Rust crate implementations.
- End-to-end swaps in both directions (BTC→LEZ and LEZ→BTC) on Bitcoin testnet and LEZ devnet/testnet using adaptor signatures on the Bitcoin side.
- Happy-path and refund-path demonstrations.
- Privacy analysis comparing HTLC vs. adaptor signature approaches and public vs. private LEZ state.
- Written feasibility report and benchmark results.
- Module/SDK and SPEL IDL for the LEZ escrow program.

### Out of Scope

- Custom LEZ tokens or ATAs (native LEZ token only; LP-0006 covers token support).
- Maker/taker model, price discovery, Logos Delivery/Chat integration (all deferred to LP-0006).
- Monero or Ethereum legs (covered in LP-0006).
- Mainnet deployment.
- Lightning Network or multi-hop swaps.
- GUI / Logos mini-app (CLI-only is acceptable for this feasibility prize).
- Ongoing maintenance or security audits beyond initial delivery.

### Known Open Problems

The following are open design questions that participants should investigate and address in their technical report:

- **secp256k1 without a Risc0 precompile**: Risc0 does not currently provide a hardware-accelerated secp256k1 precompile. If cycle counts are prohibitively high, participants should document what such an accelerator interface would look like and estimate the cycle savings it would deliver.
- **Single-transaction adaptor verification + private state**: It is not yet established whether a Risc0 guest can both verify an adaptor signature and update shielded/private LEZ state atomically in a single transaction. Participants should report what they discover.
- **Schnorr adaptor vs. ECDSA adaptor on the LEZ side**: Because LEZ keys are secp256k1-based, there may be a simpler path using ECDSA adaptors instead of Schnorr adaptors for the LEZ leg. Participants should evaluate the trade-offs.

## Infrastructure & Dependencies

- **Bitcoin**: A Bitcoin Core node or access to a Bitcoin testnet node (e.g., `bitcoind -testnet`). A wallet capable of constructing P2TR (Taproot) transactions. Familiarity with BIP-340 and BIP-341.
- **LEZ**: Access to LEZ devnet or testnet 0.2. Rust toolchain and [Risc0](https://dev.risczero.com/) development environment. Familiarity with the [Logos Execution Zone](https://github.com/logos-blockchain/logos-execution-zone/) architecture.
